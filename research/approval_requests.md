# 승인 요청 3건 — 설계·모의 테스트 완료, **실계좌 적용은 미실행**

세 건 모두 코드로 운영 동작을 바꾸지 않았다. 아래 "승인 문구"를 그대로 답해 주면
그 범위 안에서만 적용한다. 승인 없이는 연구 브랜치에만 남는다.

---

## A. 대시보드를 꺼도 보호 로직이 살아 있게 한다

**현 상태 (코드로 확정)**
`autotrade_server.py:46,69` — 스케줄러가 `threading.Thread(daemon=True)` 다.
대시보드 프로세스가 죽으면 스케줄러도 같이 죽고, 손절·만기·노출 축소도 함께 멈춘다.
모의 테스트: `research/test_ops.py::t_scheduler_dies_with_dashboard` (통과 = 결함 재현).

**상태 정의 (지금은 이름만 있고 정의가 없다 — 먼저 못박는다)**

| 상태 | 뜻 | 실제 주문 |
|---|---|---|
| `NORMAL` | 평시 | 매수·매도 모두 |
| `NEW_ENTRIES_DISABLED` | 신규 진입만 차단 | 매도만 (손절·만기·노출 축소) |
| `PROTECT_ONLY` | 보호 로직만 | **매도 주문을 실제로 낸다** — 조회 전용이 아니다 |
| `EMERGENCY_STOP` | 전면 정지 | 아무 주문도 내지 않음. 경보만 |

`PROTECT_ONLY` 가 실주문 모드라는 것은 `research/test_ops.py::t_protect_only_still_places_orders`
로 확인했다. **승인 없이 활성화하지 않는다.**

**제안**
1. `autotrade.py` 를 독립 worker 프로세스로 분리(작업 스케줄러/서비스), 대시보드는 조회 전용.
2. worker 는 시작 시 단일 실행 권한(락)을 잡고, 시작·재시작 때 `find_order` 로 대사한다.
3. 하트비트를 DB 에 남기고, N 분 이상 끊기면 경보.

**장애 시 행동**

| 시나리오 | 감지 | 보호 한계 |
|---|---|---|
| GUI 종료 | worker 는 계속 — 대시보드만 사라짐 | 사람이 상태를 못 본다 |
| worker 종료 | 하트비트 끊김 → 경보 | **자동 재시작 전까지 손절·만기가 안 나간다** |
| 네트워크 단절 | API 예외 → 경보 | 주문 자체가 불가능. supervisor 로 해결되지 않는다 |

> watchdog/supervisor 가 시장 장애나 통신 장애를 해결한다고 주장하지 않는다.
> 프로세스가 살아 있게 할 뿐이다.

**모의 테스트**: 재시작 중복 주문 없음 (`t_restart_does_not_duplicate_order`) — 같은 30분
슬롯의 같은 의도는 같은 `clientOrderId`, 브로커가 중복을 거절하고 대사로 확인되면 재제출하지 않는다.

**롤백**: worker 서비스 중지 + `autotrade_server.py` 원복 (1개 커밋 revert). 주문 상태는
DB `orders` 에 durable intent 로 남아 있어 유실되지 않는다.

**필요한 승인 문구**
> "autotrade worker 를 대시보드와 분리해 백그라운드 서비스로 설치하고 자동 시작하는 것을 승인한다.
> DRY_RUN 은 (0|1) 로 둔다. PROTECT_ONLY 활성화는 (승인|미승인)."

## B. 다중 PC 토큰 정책

**현 상태**
`toss.py:59-94` — 토큰을 `.toss_token.json` 에 원자적 교체(`tmp.replace`)로 저장하고 공유한다.
모의 테스트로 확인한 것: **같은 머신**에서 두 클라이언트가 파일을 공유하면 발급이 1회다
(`t_token_file_shared_on_same_machine`), 저장은 원자적이다(`t_token_write_is_atomic`).

**확인하지 못한 것**
토스증권 Open API 의 토큰 발급·폐기·동시 사용 정책을 **공식 문서로 확인하지 못했다.**
"신규 발급 시 이전 토큰이 무효화된다"는 기존 저장소 주석의 주장이며, 이번 작업에서
공식 사실로 재인용하지 않는다. 확인 전까지 실토큰을 새로 발급하지 않았다.

**제안 (확인 전 단계)**
1. 봇은 **한 대에서만** 실행한다 (운영 현행 유지).
2. 단일 실행 노드 후보: 공유 갱신 락 + 원자적 저장 + 리더 선출.
   `t_single_node_lock_is_machine_local` 이 보여주듯 **OS 파일 락은 머신 로컬**이다.
   다른 PC 는 그 락을 보지도 못한다 → split-brain 은 해결되지 않는다.
   다중 노드를 정말 쓰려면 공유 저장소(네트워크 FS/DB) 기반 리스 방식이 필요하다.

**장애 시 행동**: 락 취득 실패 → 해당 노드는 주문 없이 조회만. 리스 만료 시 재취득 시도.

**롤백**: 락 파일 삭제 + 단일 노드 실행으로 복귀.

**필요한 승인 문구**
> "토스 공식 문서에서 토큰 동시 사용 정책을 확인하는 것을 승인한다.
> 확인 전까지 봇은 (PC 이름) 한 대에서만 돌린다. 실토큰 신규 발급은 (승인|미승인)."

## C. QQQ 조회 실패 시 국면 지표 정책

**현 상태**
`autotrade.py:652 market_regime` — 지수를 못 받으면 **유니버스 60일 수익률 중앙값**으로
자동 전환한다. 주석 스스로 "성적이 더 낮다"고 적어 두었다. 즉 조용히 다른 전략이 된다.
모의 테스트로 실제로 판정이 갈리는 경우를 재현했다
(`research/test_safety.py::t_regime_fallback_is_a_different_strategy`: 지수 -1% → 보통,
중앙값 -8% → 하락).

**이번에 새로 찾은 결함 (N1)**
`market_regime` 은 캔들의 **최신성을 확인하지 않는다.** 몇 달 전 캔들로도 "정상 판정"을 낸다.
`research/test_ops.py::t_stale_index_is_not_detected` 로 재현했다.

**수정안 (연구 구현 완료 — `research/index_freshness.py`, 테스트 10건 통과. 운영 미적용)**

판정 기준은 **거래소 캘린더 + 마지막 완료 세션**이다. 마지막 완료 세션 =
캘린더상 오늘 이전의 마지막 거래일, 또는 오늘이 거래일이고 마감 시각이 지났으면 오늘.
정규장 마감 16:00 ET, **조기폐장일 13:00 ET**. DST 는 `zoneinfo` 가 처리한다
(오프셋을 손으로 더하지 않는다).

| 상태 | 판정 조건 | 국면 사용 | 신규 진입 | 보유분 |
|---|---|---|---|---|
| `fresh` | 마지막 봉 == 마지막 완료 세션 | 사용 | 허용 | 정상 관리 |
| `incomplete` | 마지막 봉이 진행 중인 세션 (미완성 봉) **또는** 창 안에 결측 거래일 | 보류 | 보류 | 정상 관리 |
| `stale` | 마지막 봉 < 마지막 완료 세션 (n세션 뒤짐) | 불가 | **차단** | 대사·손절·만기·노출 축소 **계속** |
| `missing` | 캔들 없음 또는 61봉 미만 | 불가 | **차단** | 대사·손절·만기·노출 축소 **계속** |

테스트로 확인한 것 (`python research/index_freshness.py`):
마감 후 fresh / 장중 incomplete / **주말은 stale 아님** / **공휴일은 stale 아님** /
조기폐장 13:00 마감(모르면 하루 뒤진 판정을 한다) / DST 경계 EST·EDT /
지연 n세션 감지 / 캔들 없음·길이 부족 / **중간 결측 gap 감지** / 대응 분리.

핵심은 **대응 분리**다. stale·missing 이라고 청산까지 멈추지 않는다 —
막는 것은 "낡은 국면 판정으로 새로 사는 일"이고, 보유분 위험 관리는 그대로 돈다.

**세 후보의 차이**

| 정책 | 장점 | 위험 |
|---|---|---|
| 운영 현행 유지 (중앙값 폴백) | 항상 판정이 나온다 | 조용히 다른 전략. 성적이 더 낮다고 적혀 있음 |
| **신규 진입만 정지 (권장 연구 후보)** | 전략을 바꾸지 않는다 | 장기 실패 시 진입 기회 상실 |
| 전면 정지 | 가장 보수적 | 보유 위험 관리까지 멈추면 더 위험 |

> 필요한 가격 자체가 없으면 "정상적으로 위험을 계산·청산할 수 있다"고 말할 수 없다.
> 그 경우 할 수 있는 것은 재조회·경보·권한 내 축소뿐이다.

**모의 테스트**: 복구 후 재개 시 중복 주문 없음 (`t_regime_recovery_no_duplicate_orders`).

**롤백**: 환경변수 한 줄 (`REGIME_FALLBACK=median`) 로 현행 복귀.

**필요한 승인 문구**
> "QQQ 조회 실패 시 유니버스 중앙값 폴백을 끄고 신규 진입만 일시 정지하도록 바꾸는 것을 승인한다.
> `research/index_freshness.py` 의 판정을 `autotrade.market_regime` 에 적용하고,
> stale 허용 임계는 (N) 세션으로 한다."

**참고 — QQQ 이력은 이번에 확보했다.** `research/data/QQQ_1d.pkl`
(Yahoo Finance via yfinance, 무료·비상업, 재배포 금지. 유료 구매·브로커 API 호출·
신규 토큰 발급 없음). 운영이 국면지표를 어디서 받을지는 별개 문제이며 여전히 토스 API 다 —
이 캐시는 **연구 재현용**이다.
